# FMS — миссия и положение робота при возникновении аварии

Оператор может открыть аварию после того, как робот восстановил связь, уехал и получил новое задание. Для разбора нужны миссия и последние достоверные координаты, известные FMS при регистрации `RAISED`.

## Что уже отдаёт сервер

Проверено по исходникам FMS, ветка `dev_traffic`, коммит `a7216bd`. Для перехода к роботу и его текущей миссии хватает действующего [контракта API](API_CONTRACT.md).

| Запрос | Данные для оператора |
| --- | --- |
| `GET /api/fms/alarms/{id}` | `robotId`, если авария относится к роботу, и время регистрации `createdAt`. Поле `missionId` уже предусмотрено. |
| `GET /api/fms/robots/{id}` | `status.connection`, `localized`, `pose` с картой и координатами, `lastNodeId`, `lastStateAt`, текущая `missionId`, когда эти данные известны. |
| `GET /api/fms/missions/{id}` | Миссия по известному ID. |

## 1. Записывать миссию при регистрации аварии

В `fleet_control/alarms/AlarmEngine.cpp` метод `raise` записывает ID робота. Здесь же стоит зафиксировать ID исполняемой миссии из известного FMS состояния робота. При отсутствии подтверждённой миссии оставить `null`. Для тревог с задержкой момент фиксации — регистрация `RAISED`.

В `AlarmEngine::save` брать ID миссии из записи аварии для всех событий её жизненного цикла — `RAISED`, `ACKED` и `CLEARED`. Тогда поиск через `GET /api/fms/events?alarmId=…` возвращает одну и ту же привязку, в том числе после смены задания или перезапуска control.

Поля `AlarmRecord.mission_id` и `Event.mission_id` уже есть в `proto/fleet_database.proto`, обе таблицы и REST поддерживают их. У `events.mission_id` есть внешний ключ на `missions`. Источником ID должна служить известная FMS миссия. Если принадлежность установить нельзя, авария и событие всё равно должны записаться.

## 2. Сохранять последнюю достоверную позицию для истории

Предлагаемое поле ответа аварии — `positionAtRaise`. Пример для случая, когда последнее сообщение с координатами пришло за пять секунд до регистрации аварии.

```json
{
  "createdAt": "2026-11-23T07:15:05.000Z",
  "positionAtRaise": {
    "mapId": "workshop",
    "x": 12.4,
    "y": 3.1,
    "theta": 1.57,
    "receivedAt": "2026-11-23T07:15:00.000Z"
  }
}
```

- Обновлять последнюю достоверную позицию при получении локализованного состояния с известной картой и конечными координатами. Хранить координаты в метрах, угол в радианах и UTC-время получения этого сообщения в dispatch.
- При потере связи или получении состояния без координат сохранять предыдущую достоверную точку вместе с её временем. Сегодня `RobotStatusBuilder.cpp` очищает текущее поле `pose` при отсутствии позиции, а `RobotSession.cpp` обновляет `lastStateAt` при получении очередного состояния. Поэтому для исторической точки нужен собственный `receivedAt`.
- При регистрации аварии записывать копию точки вместе с аварией. Для чтения из журнала достаточно `alarmId` и существующего запроса аварии по ID. Для старых аварий и роботов без известной позиции возвращать `positionAtRaise: null`.

## Приёмка на WSL

| Сценарий | Ожидаемый результат |
| --- | --- |
| Робот выполнял M1 при `RAISED`, затем начал M2. Оператор подтвердил аварию, причина ушла. | Авария и все три события содержат M1. Текущий статус робота показывает M2. |
| После последней локализованной позиции пришло состояние без координат, затем робот потерял связь. | В аварии сохранены карта, координаты и время последнего достоверного сообщения с позицией. |
| После `RAISED` перезапущен control, робот переместился. | При повторном открытии аварии и после её подтверждения видны исходная миссия и та же точка. |
| Робот ещё не сообщал позицию или работал без миссии. | Отсутствующие значения равны `null`. Остальные известные данные доступны. |
| Системная авария `SERVICE_DOWN` или старая запись с неполными данными. | Системная авария обходится без робота, миссии и позиции. Старая запись сохраняет известные поля, пропуски остаются пустыми. |

## Для следующих задач оператора

- **Причина ожидания проезда.** Сегодня `stepStates[].waitingForTraffic` позволяет показать, что робот ждёт разрешения. Для более подробного объяснения понадобятся время начала ожидания, занятый участок и ID удерживающего его робота, когда эти сведения известны планировщику.
- **Передача смены.** Для именного журнала потребуется вход под учётной записью оператора. При ручном подтверждении аварии и создании миссии серверу следует брать `acknowledgedBy` и `createdBy` из аутентифицированной сессии. Сейчас ручное подтверждение отправляется с пустым автором.
